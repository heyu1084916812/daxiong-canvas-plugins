# 融合节点插件：版本迭代与故障排查记录

记录范围：`v1.0.0`～`v2.6.0`  
当前基准版本：`v2.6.0`  
适用插件：`plugins/local-patch/`  
最后整理日期：2026-07-18

## 1. 文档目的

本文不是普通使用说明，而是插件的长期维护记录。它用于回答以下问题：

- 某项行为是在哪个版本加入的？
- 当时遇到了什么问题？
- 问题的真正根因是什么？
- 为什么采用现在的实现，而没有选择其他方案？
- 同类问题再次出现时，应按什么顺序排查？
- 更新原项目或继续迭代插件时，哪些边界不能破坏？

本文只记录已经完成并验证过的内容，截止 `v2.6.0`。不包含任何尚未实施的后续版本设想。

## 2. 不可破坏的架构原则

### 2.1 插件必须与原项目核心隔离

原项目的一键更新会覆盖 `main.py`、`VERSION`，并可能删除后重建整个 `static/`。因此插件功能不能直接写入这些核心文件。

当前方案：

- `plugin_host.py`：加载原项目 FastAPI 应用和插件。
- `plugin_runtime.py`：发现插件、注册后端路由、运行时注入前端资源。
- `start.bat`：插件模式启动入口。
- `plugins/local-patch/`：插件自己的后端、前端、测试和说明。
- `run.bat`：保持原项目无插件模式，用于隔离排查。

维护要求：

- 不修改 `main.py`、`static/`、`run.bat`。
- 新功能优先写入插件目录。
- 修改完成后核验核心文件哈希。
- 原项目接口变化时，插件应安全停用或显示兼容错误，不能阻止主程序启动。

### 2.2 所有图像处理必须是非破坏式

- 提取选区不能覆盖原图。
- 融合不能覆盖原图或局部修改图。
- 每次成功操作都创建新的图片节点和新的 PNG 文件。
- 失败时只更新节点错误状态，不创建空结果，不改变输入文件。

### 2.3 `cropContext` 是持久业务数据

`cropContext` 不是临时运行状态。它记录局部图属于哪张原图、哪个区域以及如何融合回去。

它必须经过以下路径继续保留：

- 保存和刷新画布。
- 复制、粘贴和 Alt 拖动复制。
- 单图改图、生成和 2×/4×放大。
- Output 节点和图片分组。
- 从 Output 拖回画布或在同一项目中重新导入。
- 工作流导入导出。

当多个不同上下文混入同一张结果图时，不能猜测来源，必须标记冲突并禁止融合。

## 3. 版本迭代记录

### v1.0.0：建立独立插件基础

目标：在不修改原项目核心文件的前提下，给智能画布增加局部裁剪与无缝融合能力。

主要完成：

- 建立插件宿主和运行时注入机制。
- 增加 `/api/plugins` 状态接口。
- 增加插件裁剪与融合 API。
- 智能画布增加独立局部裁剪节点和独立融合节点。
- 实现 10% 上下文扩展、SHA-256 原图校验、颜色匹配、smoothstep 羽化和原尺寸输出。
- 建立 Python 与 Node 自动化测试。

重要经验：项目自身没有稳定的公开画布插件 API，前端只能通过运行时包装已有函数接入。因此必须做接口存在性检查，并把核心算法放到独立可测试模块中。

### v2.0.1：普通画布接入与上下文重构

用户意见：裁剪不应是独立节点，应当像原项目裁剪一样内置在图片节点操作中；普通画布也需要完整流程；融合报错“缺少上下文”。

主要完成：

- 普通画布图片节点增加“提取选区”。
- 复用原项目图片编辑器，不另外制作裁剪器。
- 删除独立局部裁剪节点。
- 普通画布增加独立融合节点。
- `cropContext` 升级为持久化 v2 数据，不再强依赖已经删除的裁剪节点。
- 修复单图处理、放大和生成过程中的上下文丢失。
- 智能画布暂时只保留融合节点。

重要经验：节点已经被删除后，业务数据不能继续依赖“沿连线找到那个节点”。融合判断必须以图片自身持久化的上下文、原图指纹和尺寸为权威依据。

### v2.1.0：智能画布完整流程与统一操作栏

用户意见：智能画布也需要提取选区；入口应放在图片节点上方工具栏和双击预览编辑器中；普通画布不应额外悬浮一条只有提取按钮的工具栏。

主要完成：

- 智能画布图片节点工具栏增加“提取选区”。
- 智能画布双击预览编辑器增加“提取选区”。
- 普通画布改成统一八项图片工具栏。
- 智能融合节点改为紧凑卡片。
- 增加双图预览、状态标签、具名端口和开始融合按钮。
- 修复智能节点标题栏被核心样式隐藏的问题。

重要经验：插件入口应尽量复用原项目已经存在的交互位置。重复增加悬浮条、弹窗或按钮，会造成 UI 臃肿和维护分叉。

### v2.2.3：多图来源、结果连线与对比能力

用户意见：Output 拖回画布后上下文丢失；工具栏不会自动隐藏；Output 和分组无法作为融合输入；融合结果应通过连线生成；需要原图对比；节点自由缩放存在 UI 错位。

主要完成：

- Output 图片拖回或重新导入时恢复 `cropContext`。
- 点击画布空白区域后隐藏图片工具栏。
- Output 节点和图片分组可以连接融合节点。
- 多图节点允许在融合卡片中切换选择具体图片。
- 融合结果从融合节点通过连线生成。
- 普通、智能画布增加融合前后对比。
- 普通画布融合节点当时统一为智能卡片样式。
- 修复自由缩放与结果节点位置重叠。

重要经验：不能只保存图片 URL。Output、分组和拖拽的数据结构必须连同业务元数据一起传递。结果创建也应走统一的“创建图片节点并建立连线”流程，不能只画一条线或只写一个 URL。

### v2.3.0：清理重复的“对比原图”入口

用户意见：图片顶部工具栏和融合卡片中的对比按钮都不需要；只保留打开结果预览后右下角的原图滑杆对比。

主要完成：

- 删除图片节点工具栏中的对比入口。
- 删除融合节点卡片中的对比入口。
- 智能画布复用原生预览右下角按钮。
- 普通画布增加对应的右下角按钮，并复用原项目对比层。

重要经验：新增功能前先确认核心项目是否已经提供同类入口。插件只应补足缺失能力，不应重复实现原生功能。

### v2.4.1：智能节点缩放、对比兼容与正式发布

用户意见：智能融合节点横向或纵向缩放后，内部预览、选区和按钮不能正确适配；旧融合结果的对比按钮被禁用；插件需要可以直接发给别人使用。

主要完成：

- 修复智能融合节点横向、纵向和同时缩放。
- 内部预览、状态和按钮改为弹性布局。
- 修复旧智能融合结果只有持久图片元数据时，对比按钮无法启用的问题。
- 点击空白区域后，普通和智能图片工具栏都能隐藏。
- 增加完整安装、更新、迁移、卸载和故障排查说明。
- 制作 ZIP 和 SHA-256 发布文件，并进行模拟解压安装测试。

重要经验：预览对比不能只读取当前运行内存中的输入引用，还必须回退读取图片项的持久元数据。否则刷新页面或加载旧画布后功能会失效。

### v2.5.0：端口位置与下游结果传播

用户意见：普通融合节点端口遮挡图片；右侧端口重复；融合节点不能连接后续节点；只有连线但下游没有实际图片；智能端口也应位于整个节点边缘。

主要完成：

- 普通画布端口移到节点外边缘。
- 普通画布右侧使用共用输入/输出连接点。
- 融合节点允许连接后续生成或改图节点。
- 修复下游节点只有连线、没有融合结果缩略图的问题。
- 智能画布输入端口固定到整个节点左右边缘。

重要经验：视觉连线成功不等于数据传播成功。下游节点读取的是标准图片结果数据，因此融合成功后必须同时完成：保存文件、创建标准图片项、创建结果节点、建立连线和触发下游同步。

### v2.5.1：端口与 SVG 连线精确对齐

用户意见：智能节点缩放后端口与连线终点错位；缩小到一定程度时 UI 重叠和溢出。

主要完成：

- 连线终点改为读取实际 DOM 端口中心。
- SVG 曲线终点、端点圆点和断线按钮同步更新。
- 智能融合节点最小安全尺寸设为 `230×280`。
- 历史画布中的异常小尺寸节点自动修正。
- 修复最小尺寸下预览、状态、颜色匹配和按钮重叠。

重要经验：可缩放节点不能只用保存的 `node.w`、`node.h` 推算端口。CSS 最小尺寸、标题栏和内部布局都会改变真实位置，应以渲染后的 DOM 几何信息为准。

### v2.6.0：多轮局部修改与多选区融合

用户意见：融合完成后的图片再次提取其他区域时出现上下文冲突；一张图片可能有多个错误区域，需要多张局部修改图一次融合。

主要完成：

- 融合结果标记为新的完整图片。
- 融合结果清除上一轮局部上下文并建立上下文边界。
- 可以对融合结果重新提取、修改并再次融合。
- 单个融合节点支持最多 16 张局部修改图。
- 每条局部输入连线独立保存和选图。
- Output 或分组中的图片可以分别选择。
- 多选区按连接顺序合成；重叠时后连接的局部图覆盖前面的。
- 旧版单局部图片 API 请求继续兼容。

重要经验：完整图和局部图必须有明确的数据边界。融合结果已经恢复为完整图，不能继续继承任何输入局部图的 `cropContext`，否则第二轮操作会错误追溯到上一轮选区。

## 4. 典型问题、根因与解决方案

### P01：`start.bat` 无法启动插件模式

现象：双击 `start.bat` 后窗口退出、页面打不开，或 `plugin_host.py` 无法导入 `main.py`。

根因：项目内置 Python 使用隔离的 `python310._pth`，项目根目录没有自动加入 `sys.path`。

解决方案：在插件宿主启动早期显式注册项目根目录，再导入 `main.py` 和插件运行时。

排查：

1. 在命令行中直接运行 `start.bat`，不要只看浏览器结果。
2. 检查是否出现 `ModuleNotFoundError`。
3. 使用项目自带 `python/python.exe` 运行宿主导入测试。
4. 确认 `plugin_host.py`、`plugin_runtime.py` 与 `main.py` 位于正确层级。

### P02：普通画布有插件，智能画布没有

现象：普通画布仍能看到插件功能，但刷新或新打开的智能画布没有融合节点。

根因可能包括：

- 插件宿主已经停止，但旧普通画布页面仍保留先前加载到内存中的脚本。
- 3000 端口被 `run.bat` 或旧服务占用，浏览器连接到了无插件核心服务。
- 智能画布适配器因核心接口变化独立加载失败。
- 浏览器缓存了旧页面。

解决方案：确认插件宿主持续运行，检查 `/api/plugins`，强制刷新智能画布，并检查控制台智能适配器日志。

标准排查：

1. 打开 `http://127.0.0.1:3000/api/plugins`。
2. 确认 `compatible`、`enabled`、`loaded` 均为 `true`。
3. 确认命令行仍显示 Uvicorn 正在 3000 端口运行。
4. 关闭所有旧页面后重新运行 `start.bat`。
5. 智能画布按 `Ctrl+F5`。
6. 控制台检查 `[local-patch] smart canvas plugin 2.6.0 loaded`。

### P03：融合提示“局部图没有上下文”

现象：局部图片看起来正确，但融合节点拒绝运行。

根因：某个转换路径只复制了 URL，没有复制 `cropContext`。常见位置包括生成输出、Output、分组、拖回画布和重新导入。

解决方案：所有图片引用转换和结果创建入口统一携带 `cropContext`、冲突状态和完整图边界标记；同一项目重新导入时可通过文件指纹恢复注册表中的上下文。

排查：

1. 检查局部图片项或节点 JSON 是否存在 `cropContext`。
2. 检查它在哪一步消失：提取后、生成后、Output 中、拖回后或刷新后。
3. 只修复最早丢失的转换入口，不要在融合节点中伪造上下文。

### P04：融合提示“上下文冲突”

现象：一张处理结果无法融合，并提示包含多个不同局部上下文。

根因：来自不同原图或不同选区的局部图先进入同一个生成节点，插件无法判断最终结果属于哪个选区。

解决方案：标记 `cropContextConflict` 并阻止执行。多个选区应保持为多张独立局部图，在 v2.6.0 的融合节点中分别连接。

排查：检查生成节点全部图片输入；如果存在两个不同 `contextId`，冲突属于正确保护行为，不应强制绕过。

### P05：融合结果再次修改时出现旧上下文冲突

现象：第一轮融合成功；从融合结果重新提取另一个区域后，第二轮融合失败。

根因：融合结果错误继承了输入局部图的上下文，上游追踪又回到了上一轮局部区域。

解决方案：融合结果明确标记为完整图片，清除局部 `cropContext`，同时在上下文注册表和图结构追踪中建立停止边界。

排查：检查融合结果图片项是否仍包含上一轮 `cropContext`；完整图结果应只有原图对比等持久元数据，不应继续作为局部图传播。

### P06：一个融合节点无法接收多个选区

现象：连接第二张局部图时，第一条局部连线被替换。

根因：旧具名端口规则默认每个端口只保留一条连接。

解决方案：`original` 端口仍保持单连接；`patch` 端口允许最多 16 条连接，每条连接保存独立选择索引。后端批量校验后一次合成。

排查：检查 `patch` 连线是否被公共“单端口替换”函数清理；多连接特例必须只应用于融合节点的 `patch` 端口。

### P07：端口与连线终点错位

现象：端口视觉位置正确，但 SVG 连线结束在节点内部或旧位置；缩放后更加明显。

根因：连接曲线根据保存的节点宽高推算端口，而实际端口受标题栏、CSS、缩放和最小尺寸影响。

解决方案：渲染后读取真实端口元素的 `getBoundingClientRect()` 中心，并转换为画布坐标；曲线、端点和断线按钮使用同一坐标源。

排查：同时记录端口 DOM 中心和 SVG path 终点；两者必须完全一致。

### P08：节点缩小时 UI 重叠或溢出

现象：预览、状态标签、颜色匹配选项和执行按钮相互覆盖。

根因：节点允许缩到内部布局无法容纳的尺寸，或内部区域使用固定高度而非弹性布局。

解决方案：设置 `230×280` 最小安全尺寸；主体使用 flex 布局；预览区域允许伸缩；按钮和状态区保持固定最小高度；历史异常尺寸自动修正。

排查：分别测试横向缩放、纵向缩放、同时缩放和历史小尺寸加载，不能只测试默认大小。

### P09：融合后只有连线，下游没有图片

现象：融合节点和下游节点之间存在连线，但下游没有融合结果缩略图或输入数据。

根因：实现只更新了连接关系，没有通过画布标准结果创建和输入同步流程传播图片。

解决方案：融合成功后创建标准图片结果节点/图片项，写入自然尺寸和 URL，建立连线，再触发下游输入同步。

排查：分别检查文件是否生成、结果节点是否存在、结果图片数组是否有值、连接是否存在、下游同步函数是否执行。

### P10：“对比原图”按钮重复或刷新后被禁用

现象：图片工具栏、融合卡片和预览页同时出现对比按钮；或旧融合结果打开后按钮不可用。

根因：插件重复实现了核心已有入口；对比来源只保存在当前运行内存，刷新后丢失。

解决方案：只保留预览右下角入口；智能画布使用原生按钮；普通画布复用原生对比层；来源读取优先使用运行输入，缺失时回退持久图片元数据。

排查：确认页面只存在一个用户可见入口；刷新画布后再次验证按钮状态和原图 URL。

### P11：Output、分组或重新导入后上下文丢失

现象：原局部图可以融合，进入 Output、分组或拖回画布后不能融合。

根因：容器只保存展示字段，或者拖拽载荷只携带 URL。

解决方案：图片引用、拖拽载荷和注册表都携带持久上下文；导入时按稳定文件指纹恢复。

排查：对比进入容器前后的图片项 JSON，不要只观察节点外观。

### P12：插件包中出现临时目录或旧版本文件

现象：`dist` 中出现 `local-patch-*-stage-*`、旧 ZIP 或其他暂存内容。

根因：打包过程使用暂存目录，清理步骤未完成；`dist` 同时被当成发布目录和历史备份目录。

解决方案：正式发布后只保留当前 ZIP 和对应 SHA-256；暂存目录必须为空并删除。需要保留历史版本时，应另建归档目录。

排查：发布前列出 ZIP 内容，确认不包含缓存、测试产物、用户图片、`main.py`、`run.bat` 或 `static/`。

## 5. 标准维护排查流程

### 5.1 插件完全没有出现

```text
start.bat 窗口是否仍在运行
→ 3000 端口是否为插件宿主
→ /api/plugins 是否存在
→ compatible/enabled/loaded 是否全部为 true
→ 页面是否加载 local-patch JS/CSS
→ Ctrl+F5 排除缓存
→ 查看控制台插件日志
```

### 5.2 只有一个画布出现插件

```text
检查普通和智能页面各自注入的适配器
→ 检查对应适配器兼容性断言
→ 检查页面缓存与打开时间
→ 检查两个页面控制台错误
→ 不要用另一个画布正常作为当前画布正常的证据
```

### 5.3 提取正常但融合失败

```text
检查原图输入
→ 检查局部图 cropContext
→ 检查 contextId/原图 SHA-256/尺寸
→ 检查 cropContextConflict
→ 检查局部图宽高比
→ 检查是否把完整融合结果错误当成局部图
→ 检查后端错误响应
```

### 5.4 UI 或连线错位

```text
测试默认尺寸
→ 测试横向缩放
→ 测试纵向缩放
→ 测试最小尺寸
→ 对比端口 DOM 中心与 SVG 终点
→ 检查断线按钮和端点圆点是否使用同一坐标
→ 检查历史节点尺寸自动修正
```

### 5.5 修改完成后的固定验证

```powershell
.\python\python.exe -m unittest discover -s plugins\local-patch\tests -p "test_*.py"
node --test plugins\local-patch\tests-js\*.test.js
node --check plugins\local-patch\web\local-patch-core.js
node --check plugins\local-patch\web\local-patch.js
node --check plugins\local-patch\web\local-patch-classic.js
```

还必须执行：

- 普通画布真实页面验收。
- 智能画布真实页面验收。
- 浏览器控制台错误检查。
- `/api/plugins` 状态检查。
- 原图、局部图和融合结果文件不被覆盖的哈希检查。
- `main.py`、`run.bat`、`static/` 核心隔离检查。
- 发布 ZIP 模拟解压安装。

## 6. 后续开发可复用的经验

1. **先找原项目已有入口，再决定是否新增 UI。** 重复入口会造成用户困惑和额外维护成本。
2. **业务元数据必须和图片一起流动。** 只传播 URL 的实现迟早会在 Output、分组、复制或刷新时失效。
3. **完整图与局部图必须有数据边界。** 多轮编辑是否可靠，取决于是否正确终止旧上下文传播。
4. **连线显示和数据传播要分别验证。** 有 SVG 连线不代表下游真正收到图片。
5. **动态尺寸必须读取真实 DOM。** 仅根据保存宽高推算端口，无法覆盖 CSS 和历史数据影响。
6. **普通画布和智能画布是两个独立适配器。** 一边正常不能证明另一边正常，测试必须分开。
7. **插件模式与无插件模式必须长期并存。** `start.bat` 用于正常插件使用，`run.bat` 用于判断故障是否来自插件。
8. **版本发布必须可复现。** 测试、核心哈希、ZIP 内容、模拟安装和 SHA-256 都应成为发布步骤。
9. **错误保护不能为了“能运行”而绕过。** 指纹不一致、上下文冲突和比例错误是在阻止错位融合，应修复数据来源而不是关闭校验。
10. **每次修复都应补回归测试。** 尤其是上下文传播、具名端口、多连接、缩放和旧画布加载。

## 7. v2.6.0 当前能力基线

截至 `v2.6.0`，以下能力应视为回归基线：

- 普通和智能画布都能提取局部选区。
- 原图始终不被提取或融合操作覆盖。
- 单图编辑、生成和 2×/4×放大保留上下文。
- Output、分组和同项目重新导入支持上下文恢复。
- 融合节点接受一张原图和最多 16 张局部修改图。
- 多选区按连接顺序融合。
- 融合结果是新的完整图片，可继续进行下一轮提取与融合。
- 普通和智能画布都在结果预览右下角提供原图滑杆对比。
- 端口位于节点外边缘，并与连线终点对齐。
- 节点最小尺寸下不发生 UI 重叠。
- 融合结果能够通过连线提供给后续节点。
- 插件继续独立运行，不修改原项目核心文件。

后续任何版本修改，都应先验证以上基线没有退化。
